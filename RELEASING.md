# Releasing

The workspace version in `Cargo.toml` is always the next release. Releasing
publishes that version and then bumps to the one after it. Versioning rules are
in [STABILITY.md](STABILITY.md).

1. Land everything on `master` with CI green, and check out a clean, up to date
   `master`.
2. Run the release checks: fmt, clippy, the workspace and `linux-full` suites,
   a current `docs/elements.html`, the API-break list, and a publish dry run.

   ```sh
   tools/release.sh check
   ```

3. Log in to crates.io (the token is never stored in the repo):

   ```sh
   cargo login <token>
   ```

4. Publish. This moves the `## Unreleased` CHANGELOG entries under a heading
   for the version, commits `release X.Y.Z`, tags `vX.Y.Z`, publishes every
   crate in dependency order, then pushes `master` and the tag.

   ```sh
   tools/release.sh publish
   ```

5. Bump to the next version. Before 1.0 a breaking change needs the next minor
   (`0.9.0` to `0.10.0`), see STABILITY.md.

   ```sh
   tools/release.sh bump 0.10.0
   git push origin master
   ```

## Notes

- `publish` can be rerun after a failure. It skips the tag step once the tag
  exists and skips every crate already on crates.io at that version.
- crates.io limits how fast crates are published. On a failed upload the
  script waits 10 minutes and retries the same crate.
- The tag push runs `.github/workflows/release.yml`, which builds `g2g-launch`
  and `g2g-inspect` for Linux, macOS and Windows and attaches them to the
  GitHub release. Run it by hand from the Actions tab to test the builds without
  a tag. The feature sets are the `release-binary-*` features of g2g-plugins.
- The same workflow wraps the Linux build in `.deb` and `.rpm` packages with
  nFPM, from `tools/nfpm.yaml`. It installs them in clean containers and runs
  a smoke pipeline before the release is created.
- The same workflow builds a Windows `.msi` from `tools/glass2glass.wxs` with
  WiX, and installs, runs and uninstalls it before the release is created.
- After the release, the workflow writes `Formula/glass2glass.rb` to
  `Glass2GlassHQ/homebrew-tap`, using the `HOMEBREW_TAP_DEPLOY_KEY` secret. The
  `homebrew-install` job tests the same formula from a local tap first.
- The `maven-central` job is commented out. Enabled, it uploads the AAR to the
  Central Portal after the release, using the `MAVEN_GPG_PRIVATE_KEY` and
  `MAVEN_CENTRAL_TOKEN` secrets. The upload waits for a manual publish in the
  portal, and a published version cannot be removed.
- The same workflow builds the `glass2glass` wheels and uploads them to PyPI
  through trusted publishing, so no PyPI token is stored anywhere. The upload
  waits for approval in the `pypi` environment.
- The same workflow attaches the Android AAR that `tools/android-aar.sh` builds.
- Every archive, wheel and AAR carries `LICENSE-THIRD-PARTY.txt`, generated by
  cargo-about from `about.toml` and `about.hbs`. A dependency whose licence is
  not in the `accepted` list of `about.toml` fails the release build.
- `g2g-pyapi`, `xtask` and the benchmark and web crates are `publish = false`.
  The Python wheel is built with maturin, not published by this script.
